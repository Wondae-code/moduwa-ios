### 1묶음 · 버그 둘 (먼저)

UI를 건드리기 전에 잡는다. 화면이 바뀐 뒤에 버그를 재현하면 무엇 때문인지 헷갈린다.

**#15 글자 크기 → 메인 복귀 — 원인 확인됨**

`moduwa/Services/AccessibilitySettings.swift` 의 `applyTextScale(_:)` 가

```swift
if let size = scale.dynamicTypeSize { dynamicTypeSize(size) } else { self }
```

이다. `@ViewBuilder` 의 if/else 는 `_ConditionalContent` 를 만들어 **분기가 바뀌는 순간 뷰
정체성이 바뀐다**. 이 모디파이어가 `RootView.body` 의 `tabs` 전체에 걸려 있어서(`RootView.swift:69`),
**시스템 ↔ 크게**로 넘어갈 때 SwiftUI 가 트리를 통째로 새로 만들고 각 탭 `NavigationStack` 의
경로가 날아간다 → 메인으로 돌아간다.

**→ 고쳤다(2026-09-06).** `transformEnvironment(\.dynamicTypeSize)` 로 바꿔 **어떤 단계에서도
모디파이어가 늘 하나**만 걸리게 했다. `.system` 이면 물려받은 값을 건드리지 않아 결과는 예전과
같고, 분기가 없어져 정체성도 안 바뀐다. 이유는 그 함수 주석에 남겼다.

시뮬레이터 확인(iPhone 17 Pro, iOS 26.4) — 홈 → 설정 → 접근성까지 두 단 들어간 상태에서
**시스템 → 크게 → 아주 크게 → 시스템**을 모두 옮겼고, 매번 접근성 화면에 그대로 남았다.
글자도 단계마다 실제로 커졌다(모디파이어가 헛돌지 않는다는 확인).

같은 함수를 쓰는 `AccessibilitySettingsView` 의 미리보기 카드도 함께 고쳐졌다.

**#4 홈 최신 피드 — 고쳤다(2026-09-06). 원인이 셋이었다.**

라이브 서버에 직접 물어 확인했다(`GET /v1/reviews`):

| 정렬 | 첫 5건의 작성일 |
|------|----------------|
| `recommended`(앱의 옛 기본값) | 07-11, 07-09, 07-07, 07-12, 06-30 — **전부 두 달 전** |
| `latest` | **09-06**, 08-22, 08-09, 08-08, 08-08 |

그날(09-06) 올라온 후기 "허스크밀"은 반응이 0 이라 추천순 12건 중 뒤로 밀려 **첫 페이지에
아예 없었다.** 앱을 처음 켠 사람이 두 달 전 글을 봤다. 원인 셋을 모두 고쳤다:

1. ~~기본 정렬을 `.recommended` → `.latest`~~ → **되돌렸다(추천 우선 유지, 기획 결정).**
   따라서 **최신 글이 위로 오지 않는 것은 지금도 그대로다.** 새 글을 위로 올려야 한다면
   정렬 기준 자체를 손대야 한다(아래 "추천 기준" 참고) — 서버 일이다.
2. **홈에 당겨서 새로 고침을 붙였다**(`HomeViewModel.refresh`). 홈에는 다시 받을 길이
   아예 없었다 — `.task` 는 돌아올 때 다시 돌지 않는다. 저장·내 글·차단 목록에는 이미
   있던 동작이다. 실패한 목록은 지우지 않는다(당긴 순간 네트워크가 흔들리면 보던 것이 사라진다).
3. **후기를 쓰면 홈에 알린다**(`PostInteractionSignal.reviewWritten()`). 게시글은
   `WriteFloatingButton.onPosted` 로 이미 알렸지만 **후기는 장소 상세에서 쓰기 때문에 홈이
   그 일을 몰랐다** — 앱을 다시 켜야 보였다. 후기를 쓰는 두 화면(장소 상세·장소 후기 목록)이
   신호를 올리고 홈이 `.task(id:)` 로 지켜본다.

시뮬레이터 확인(iPhone 17 Pro): 정렬 칩이 "최신"으로 뜨고 **그날 쓴 후기가 피드 첫 줄**에
올라왔다(고치기 전에는 목록에 없었다). 당겨서 새로 고침은 "맞춤 추천 더보기"로 2페이지까지
늘린 뒤 당기면 목록이 1페이지로 되돌아가는 것으로 확인했다.

⚠️ 3번(후기 신호)은 **로그인이 필요해 시뮬레이터에서 끝까지 못 봤다** — 실기기 확인 목록.

**추천 기준(서버 `REVIEW_ORDERS`, `src/server/app.ts:934`)**

| sort | ORDER BY |
|------|----------|
| `recommended` (기본) | `(like_count + comment_count) desc, created_at desc` |
| `latest` | `created_at desc` |
| `likes` (장소 후기 화면 전용) | `like_count desc, created_at desc` |

좋아요와 댓글을 **1:1 로 더한 값**만 본다. 최신성은 그 합이 같을 때의 두 번째 키일 뿐이라
반응이 하나라도 붙은 오래된 글이 갓 올라온 글보다 늘 위에 선다. 시간 감쇠(오래된 반응의
가중치를 낮추는 것)는 없다.

`/v1/posts` 에는 **정렬 파라미터가 아예 없다**(`created_at desc` 고정) — 그래서 앱이
`HomeViewModel.feedItems` 에서 게시글에 같은 규칙을 다시 적용해 섞는다.

### 추천 기준을 접근성 우선으로 바꿨다(2026-09-06)

기본 정렬은 추천으로 두고, **추천의 뜻**을 고쳤다. 앱의 `.recommended` 는 이제

**① 내 무장애 축과 겹치는 수 → ② 반응 수 → ③ 최신**

순으로 세운다(`HomeViewModel.feedItems`). 접근성이 주제인 앱에서 "추천"이 반응 수만
뜻하면 나와 상관없는 조건의 글이 위에 선다 — 휠체어로 다니는 사람에게 시각장애 후기가
인기순으로 먼저 오는 식이다. **서버 `REVIEW_ORDERS` 와 일부러 달라진 자리다.**

"이 글이 어떤 축인가"는 두 종류가 다른 자리에 담고 있어 `HomeFeedItem.accessFeatures` 가
한 뜻으로 모은다 — 후기는 **방문 조건 태그**(`visit_*`), 게시글은 `accessFeatures`.
겹침을 여부(0/1)가 아니라 **개수**로 세므로 축을 둘 고른 사람에게 둘 다 맞는 글이 위로 온다.
축을 고르지 않은 사람(해당없음·비로그인)은 겹침이 늘 0 이라 예전과 똑같이 동작한다.

**함정 하나(실측으로 걸렸다)** — 후기 태그를 `kind == .visitor` 로 걸러선 안 된다.
`GET /v1/reviews` 항목의 태그에는 **`kind` 가 실리지 않는다**(`reviewSelect`, app.ts:891 —
`code`·`label`·`shortLabel`·`icon` 뿐). `kind` 는 정의 목록 `GET /v1/review-tags` 에만 있다.
그래서 `ReviewTag.kind` 는 기본값 `.place` 로 디코드되고, `kind` 로 걸렀다면 방문 조건 태그가
**하나도** 걸리지 않았다. 코드로 되찾으면(`AccessibilityFeature(visitorTagCode:)`)
`visit_*` 만 정확히 맞으므로 가를 필요가 없다.

**시뮬레이터 확인** — 내 축을 "시각 지원"으로 두고 정렬을 추천으로 둔 상태에서,
반응 0 인 게시글("오뎅탕", wheelchair+visual)이 반응 6 인 글("안녕")을 **제치고 1위**로 왔다.

⚠️ **아직 반쪽이다 — 받아 온 것 안에서만 다시 세운다.**
서버는 여전히 반응 수 순으로 페이지를 자른다. 게시글은 10건을 한 번에 받아(전체가 10여 건)
사실상 전부 대상이지만, **후기는 첫 페이지 5건뿐**이다. 실제로 시각 축에 맞는 후기
"허스크밀"(`visit_visual`, 반응 0)은 반응 수로 12건 중 6위라 **2페이지에 있어 홈에 못 온다.**
막으려면 셋 중 하나가 필요하다:

**→ 2번(서버)으로 간다. 요청서를 냈다: `docs/BACKEND_REQUEST_access-first-recommend.md`**
(2026-09-06). `GET /v1/reviews?sort=recommended` 에 `myVisitorTags` 를 받아 정렬 1순위 키로
쓰는 요청이다. **앱 쪽은 파라미터 이름이 확정되면 한 줄**이라 그때 붙인다 — 그동안 앱의
페이지 안 재정렬은 그대로 동작한다.

검토했다가 접은 것:
1. 앱에서 `visitorTag` 필터로 한 번 더 받아 앞에 붙이기 — 축 하나당 요청 하나가 늘고,
   두 목록의 페이지네이션을 앱이 또 관리해야 한다.
3. 그대로 두기 — 후기가 쌓이면 확률은 올라가지만 지금 데이터로는 효과가 0 이다.

⚠️ 1·2 모두 **무장애 축을 서버로 보낸다.** 참고로 지금도 홈은 추천 장소를 받을 때
`access=<groups>` 를 쿼리로 보내고 있다(`APIFeedService.fetchRecommendedPlaces`) —
새로운 종류의 전송은 아니지만, 쿼리스트링은 서버 접속 로그에 남는다는 점은 별개로 짚어 둘 만하다.
