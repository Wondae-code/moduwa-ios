### ~~🚧 임시로 넣은 것~~ → 해결(2026-09-07)

**플랜·일정 카드의 기본 표지.** 담긴 장소에 사진이 하나도 없으면 카드가 빈 회색이라 짜임을
볼 수 없어서, UI 확인용으로 경주(동궁과 월지) 사진 두 장을 깔아 뒀었다.

⚠️ 그게 **제주 플랜에도 경주를 띄웠다** — 없는 정보를 비워 두는 것보다 **틀린 정보를 주는
쪽이 나쁘다.**

**→ `PlanCoverPlaceholder`(옅은 회색 `#EBEBEB`)로 끝냈다.** 경주 사진 두 장은 지웠다.
가는 길에 셋을 만들어 보고 버렸다:

| 안 | 왜 버렸나 |
|---|---|
| 지역별 그림 | 지역 수만큼 필요하고 새 지역마다 빈자리가 생긴다 |
| 브랜드 무늬(라임 스우시) | 표지가 제목·날짜 앞에 섰다 |
| 라임 단색 | 같은 이유 — **카드가 화면을 다 가져갔다** |

최종은 **`cardStroke` 토큰(#E6E6E6)** 이다. 하드코딩하지 않는 이유는 고대비에서 `#8C8C8C` 로
짙어져 흰 글자에 그만큼 도움이 되기 때문이다.

⚠️ **글자는 흰색으로 두기로 했다**(2026-09-07 결정). 잠깐 딥그린으로 바꾸고 스크림을 걷어
14:1 을 만들었다가 되돌렸다. 화면에서 픽셀을 직접 재면(iPhone 17 Pro):

| 자리 | 배경 | 흰 글자 대비 |
|---|---|---|
| 제목 줄 | `rgb(177,177,177)` | **2.14:1** |
| 날짜 줄 | `rgb(143,143,143)` | 3.23:1 |
| 카드 위쪽(스크림 밖) | `rgb(230,230,230)` | 1.25:1 |

본문 최소 4.5:1 에 못 미친다. **사진 표지에서는 문제가 없고 기본 표지에서만 나오는 값이다.**
되돌리려면 글자를 `textPrimary` 로 바꾸고 그 경우에만 스크림을 걷으면 된다(`hasPhoto` 분기).

일정 카드는 표지와 **흐린 사본을 겹치는** 처리가 있는데, 한 색에는 겹칠 것이 없어 그대로
채운다. `layered(_ image: Image)` 는 `layered { }` 로 일반화해 뒀다 — 받아 온 사진과 기본
표지가 같은 처리를 받는 자리를 하나로 유지하기 위해서다.

### 1묶음 · 버그 둘 (먼저)

UI를 건드리기 전에 잡는다. 화면이 바뀐 뒤에 버그를 재현하면 무엇 때문인지 헷갈린다.

**#15 글자 크기 → 메인 복귀 — 원인 확인됨**

`moduwa/Services/AccessibilitySettings.swift` 의 `applyTextScale(_:)` 가

```swift
if let size = scale.dynamicTypeSize { dynamicTypeSize(size) } else { self }
```

이다. `@ViewBuilder` 의 if/else 는 `_ConditionalContent` 를 만들어 **분기가 바뀌는 순간 뷰
정체성이 바뀐다**. 이 모디파이어가 `RootView.body` 의 `tabs` 전체에 걸려 있어서(`RootView.swift:69`),
**시스템 ↔ 크게**로 넘어갈 때 SwiftUI 가 트리를 통째로 새로 만들고 각 탭 `NavigationStack` 의
경로가 날아간다 → 메인으로 돌아간다.

**→ 고쳤다(2026-09-06).** `transformEnvironment(\.dynamicTypeSize)` 로 바꿔 **어떤 단계에서도
모디파이어가 늘 하나**만 걸리게 했다. `.system` 이면 물려받은 값을 건드리지 않아 결과는 예전과

**시스템 → 크게 → 아주 크게 → 시스템**을 모두 옮겼고, 매번 접근성 화면에 그대로 남았다.

`HomeViewModel.feedItems` 에서 게시글에 같은 규칙을 다시 적용해 섞는다.

### 추천 기준을 접근성 우선으로 바꿨다(2026-09-06)

기본 정렬은 추천으로 두고, **추천의 뜻**을 고쳤다. 앱의 `.recommended` 는 이제

**① 내 무장애 축과 겹치는 수 → ② 반응 수 → ③ 최신**

순으로 세운다(`HomeViewModel.feedItems`). 접근성이 주제인 앱에서 "추천"이 반응 수만
뜻하면 나와 상관없는 조건의 글이 위에 선다 — 휠체어로 다니는 사람에게 시각장애 후기가
인기순으로 먼저 오는 식이다. **서버 `REVIEW_ORDERS` 와 일부러 달라진 자리다.**

"이 글이 어떤 축인가"는 두 종류가 다른 자리에 담고 있어 `HomeFeedItem.accessFeatures` 가
한 뜻으로 모은다 — 후기는 **방문 조건 태그**(`visit_*`), 게시글은 `accessFeatures`.
겹침을 여부(0/1)가 아니라 **개수**로 세므로 축을 둘 고른 사람에게 둘 다 맞는 글이 위로 온다.
축을 고르지 않은 사람(해당없음·비로그인)은 겹침이 늘 0 이라 예전과 똑같이 동작한다.

**함정 하나(실측으로 걸렸다)** — 후기 태그를 `kind == .visitor` 로 걸러선 안 된다.
`GET /v1/reviews` 항목의 태그에는 **`kind` 가 실리지 않는다**(`reviewSelect`, app.ts:891 —
`code`·`label`·`shortLabel`·`icon` 뿐). `kind` 는 정의 목록 `GET /v1/review-tags` 에만 있다.
그래서 `ReviewTag.kind` 는 기본값 `.place` 로 디코드되고, `kind` 로 걸렀다면 방문 조건 태그가
**하나도** 걸리지 않았다. 코드로 되찾으면(`AccessibilityFeature(visitorTagCode:)`)
`visit_*` 만 정확히 맞으므로 가를 필요가 없다.

**시뮬레이터 확인** — 내 축을 "시각 지원"으로 두고 정렬을 추천으로 둔 상태에서,
반응 0 인 게시글("오뎅탕", wheelchair+visual)이 반응 6 인 글("안녕")을 **제치고 1위**로 왔다.

**→ 서버가 붙였다(2026-09-07, 052). 이제 페이지 밖의 일치도 올라온다.**

쿼리가 아니라 **헤더 `x-visitor-tags`** 다. 서버팀이 프로브로 확인해 보니 접속 로그에는
쿼리가 애초에 안 남는데(`srcIp` 만 남는다), **로그가 아니라 URL 자체가 새는 경로**여서
헤더로 갔다 — 이슈에 붙는 curl 한 줄, 화면 캡처, 채팅에 붙여넣는 재현 절차. 누가 디버깅하다
URL 을 티켓에 붙이면 그 순간 한 사람의 장애 축이 트래커에 들어간다. 맞는 판단이다.

앱이 붙인 것:
- `ModuwaAPI.attach(visitorTags:to:)` 한 곳에서 헤더를 만든다.
- `fetchReviews(sort:page:accessFeatures:)` — **추천 정렬에서만** 싣는다.
- **장소 목록의 `access=` 쿼리도 같은 헤더로 옮겼다.** 서버가 `visit_` 접두어를 떼고 보므로
  값은 그대로다. 옛 쿼리도 서버가 아직 받지만(심사 중인 빌드가 쓴다) 새로 보내는 쪽은 헤더만.

실측(2026-09-07): 헤더 없이 `[2,3,4,1,6]` → `x-visitor-tags: visit_visual` 로 `[15,2,3,4,1]`.
`sort=latest` 는 안 바뀐다. 모르는 코드는 200 에 0점. 장소 목록도 헤더로 좁혀지는 것을
앱에서 눈으로 확인했다(유아동반 계정에 유모차·수유실 장소가 떴다).

⚠️ 서버가 **`likes` 에도 적용하지 않았다** — 요청서에는 `sort !== 'latest'` 로 적었는데,
장소 후기 화면의 "좋아요 순" 칩은 **사용자가 직접 고른 순서**라 앞에 키를 세우면 그 라벨도
거짓말이 된다는 이유다. 우리가 `latest` 를 뺀 이유가 그대로 걸린다 — 맞는 지적이다.

⚠️ 헤더는 **다섯 개까지**만 보고 뒤는 조용히 버린다(`slice(0, 5)`, 앞에서 자른다).
축이 다섯뿐이라 걸릴 일은 없지만 순서에 뜻을 담지 않는다.

⚠️ **`kind` 가 실렸지만 앱은 계속 코드로 되찾는다.** 서버 문서에도 "`visit_` 접두어로
판별하지 말 것" 이라고 적혔는데, `AccessibilityFeature(visitorTagCode:)` 는 접두어가 아니라
**`visitorTagCode` 표를 뒤집어** 찾으므로 그 함정에 안 걸린다(코드 표가 곧 규칙이다).

#### 축 이름이 어긋나면 양쪽 다 조용히 틀린다 (2026-09-07)

서버팀이 오타 하나의 방향을 지적했다 — 실측으로 확인했다:

```
(헤더 없음)        10,273        visit_wheelchair   9,280
visit_wheelchiar   10,273  ←     wheelchair         9,280   (접두어 없이도 같다)
visit_visul        10,273  ←     visit_visual       3,431
                                 visit_hearing        107
                                 visit_infant       3,003
                                 visit_elderly      6,236
```

모르는 축은 400 이 아니라 **필터가 통째로 사라진다.** 목록이 비면 사용자가 알아채지만
늘어나면 아무도 모른다 — 휠체어 이용자가 휠체어로 못 가는 곳을 추천받고 화면은 멀쩡하다.

**앱에도 같은 병이 있고 방향만 반대다.** 서버가 축 이름을 바꾸면
`AccessibilityFeature(visitorTagCode:)` 가 nil 을 주고 `compactMap` 이 버려서, 홈 추천이
"나와 같은 조건" 을 하나도 못 세고 **참여수 순으로 되돌아간다.** 오류도 빈 목록도 없이
추천의 뜻만 바뀐다.

→ `ReviewTagDTO.tag`(`APIFeedService`)에 **DEBUG 전용 그물**을 뒀다. `kind == .visitor`
인데 표에 없는 코드가 오면 `Logger.fault` 로 남긴다. **`visit_` 접두어로 판별하지 않는다**
— 접두어는 서버가 바꿀 수 있고 그러면 그물 자체가 조용히 빈 그물이 된다(서버팀 당부).
터뜨리지 않는 이유: 서버가 **축을 더하는 것**은 회귀가 아닌데 `assertionFailure` 는 이름
변경과 구별하지 못하고, 기기에 꽂아 QA 하는 중에 태그 코드 하나로 앱을 멈춰 세운다.

서버팀이 "아는 축 목록을 응답에 실어 드릴까" 했는데 **사양했다** — 어긋남을 찾아도 릴리스
빌드가 할 수 있는 일이 없어서, 결국 지금 그물과 같은 개발 시점 확인으로 끝난다.
서로 축 이름을 건드리기 전에 알리는 쪽이 실제로 막아 준다.

#### 같은 다섯 축이 세 벌의 이름으로 있다 (2026-09-07)

```
축     rawValue                    ?access=     visitorTagCode
       access_features(030·027)                 review_tag_defs(051)
지체   wheelchairAccessible        wheelchair   visit_wheelchair
시각   visuallyImpairedFriendly    visual       visit_visual
청각   hearingFriendly             hearing      visit_hearing
유아   childFriendly               infant       visit_infant   ← 어간이 다르다
고령   elderlyFriendly             elderly      visit_elderly
```

실측(`GET /v1/posts`, 2026-09-07): `['childFriendly', 'visuallyImpairedFriendly',

틀렸다 — `serverAccessGroup`(`?access=` 어휘)을 보고 넘겨짚었고 `rawValue` 를 안 봤다.
서버팀이 프로덕션 값을 세어 바로잡았다.

⚠️ **접두어를 떼서 오갈 수 없다.** 다섯 중 넷이 우연히 겹칠 뿐이고 유아 축은
`childFriendly` ↔ `infant` 라 어떤 문자열 규칙으로도 못 간다. 세 `switch` 가 규칙이다.

→ `AccessibilityFeature` 선언 위에 표를 적어 뒀다(`Place.swift`). 서버 쪽은 같은 내용이
`sql/052_tag_defs_restrict.sql` 주석에 반대 방향으로 적혀 있다 — 이름을 바꾸려는 사람이
어느 쪽 파일을 열든 나머지 둘을 보게 된다.

⚠️ `access_features` 에 CHECK 는 **일부러 안 건다**(서버팀). 걸면 앱이 축을 늘릴 때마다
서버 배포가 먼저여야 하고, 순서가 어긋나면 가입·프로필 저장이 400 이 된다(050 때 실제 사고).

#### 3/6 다른 일정: 표시 → 제약, 그리고 드래그 (2026-09-07 추가 요청)

**① 다른 일정 날짜는 고를 수 없다.** 처음에는 "알려 주기만 하는 표시" 로 뒀는데 되돌렸다 —
회색으로 칠해 둔 이유가 "여기는 이미 찼다" 이므로 눌리지 않는 게 앞뒤가 맞는다.
범위도 그 날짜를 **넘어갈 수 없다**(사이에 못 고르는 날을 끼운 기간은 만들 수 없다).
날짜 색은 `iconGray` 가 아니라 `textSecondary` 다 — `#E6E6E6` 알약 위에서 `iconGray` 는
1.9:1 로 읽을 수 없다(시안도 이 칸을 `#4D4D4D` 로 그려 둔다, 7.4:1).

**② 꾹 눌러 끌면 기간이 잡힌다.** 칸을 0.25초 누른 뒤 끌면 그 날짜를 기준점으로 양쪽으로
늘어난다. 벽(다른 일정·지난 날짜)에 닿으면 **거기서 멈춘다** — 손으로 막히는 것을 안다.

함정 둘을 실측으로 밟았다:
- **`DragGesture.startLocation` 은 누른 점이 아니다** — 누른 뒤 *첫 이동 지점*으로 들어온다.
  그래서 출발 칸을 놓치고, 특히 다른 일정 위를 지나가면(그 칸은 위치를 안 올린다) 한참 뒤
  칸이 기준점이 됐다. → 기준점은 **칸이 스스로 알린다**(칸마다 `LongPressGesture`).
- **벽 판정은 기준점에서 걸어야 한다.** 범위의 아래쪽 끝에서 걸으면 방향에 따라 달라져,
  26일에서 왼쪽으로 끌 때 22~25일 벽을 뛰어넘어 21일이 잡혔다.

**③ 누름 없이 바로 끌리게 해 봤다가 되돌렸다**(2026-09-07: "별론데? 롤백하자").

세로 `ScrollView` 와 다투는 것을 방향으로 가르려면 SwiftUI `DragGesture` 로는 안 되고
(**활성화되는 순간 스크롤 팬을 먹는다** — 관례가 "꾹 누른 뒤 끌기" 인 이유가 그것이다)
UIKit 인식기까지 내려가야 했다. 그렇게까지 해서 얻은 손맛이 좋지 않았다. 그 과정에서 밟은
함정 둘은 다시 시도할 사람을 위해 남겨 둔다:

- **방향을 격자 좌표계에서 재면 세로 스와이프가 기간을 잡는다**(실측: 위로 훑으니
  10/1~10/8 이 선택됐다). 스크롤하는 좌표계에서는 **콘텐츠가 손가락과 함께 움직여 세로
  변위가 0 에 가까워지고**, 남은 가로 흔들림이 우세해진다.
- **`updateUIView` 시점에는 상위 뷰 사슬이 아직 없다** — 스크롤 뷰를 못 찾아 팬이 아예 안
  걸린다. `didMoveToWindow` 에서 붙여야 한다.

**④ 누름은 기다림이 아니라 신호로 쓴다.** 0.25초 뒤 **햅틱이 한 번 울려** "이제 끌 수 있다"를
손으로 알린다. 화면만 보고는 언제부터 끌리는지 알 수 없었는데 그 틈을 이게 메운다.
누름만으로 하루가 잡힌 것도 결과라, 끌지 않고 떼는 사람에게도 낭독한다.

**⑤ 벽에도 햅틱.** 둘은 느낌이 달라야 구별된다 — 잡힘은 `.impact(weight: .medium, 0.9)`
묵직하게, 벽은 `.impact(flexibility: .rigid, 0.6)` 얇고 딱딱하게. 벽은 **처음 닿는 순간에만**
울린다(붙어 있는 동안 계속 울리면 소음이다). 눈으로만 알리면 화면을 보지 않는 사람에게는
아무 일도 없는 것과 같다 — 값이 안 바뀌니 낭독도 안 된다.

확인(iPhone 17 Pro): 꾹 누른 뒤 드래그 15→19 ✓, 21→26 이 **21 에서 멈춤** ✓,
다른 일정 탭 무반응 ✓, 탭 13→17 ✓. **햅틱 두 가지는 실기기에서 확인 필요.**

⑨ 목록을 못 받으면 조용히 안 그린다(실패를 오류로 띄우면 없던 규칙이 생긴다).
회색은 눈에만 보이므로 날짜 칸의 접근성 값에 "다른 일정 있음" 을 함께 실었다.

**실기기에서 잡힌 것 둘**(2026-09-07):

- **날짜마다 동그라미가 보였다.** 회색 띠를 `rangeBand` 처럼 *칸마다 캡슐 + 좌우 반쪽
  사각형*으로 겹쳐 그렸더니, **같은 색이어도 캡슐 테두리의 안티에일리어싱이 사각형 위에
  겹쳐 링으로 남았다.** → 겹치는 도형을 없애고 **모서리만 조건부로 둥근 사각형 한 장**을
  칸 폭에 꽉 채운다(`UnevenRoundedRectangle`). 옆 칸과 정확히 맞닿고 구간의 양 끝만 둥글다.
- **"다른 일정" 이 있는 주만 높아졌다.** 글자가 줄 아래에서 레이아웃 공간을 차지해서다.
  칸 사이 여백은 **15pt**(칸 44 − 원 32 의 위아래 6 + 줄 간격 3)뿐이라 12pt 글자를 끼울
  자리가 없다 — 겹치지 않게 두려면 결국 줄을 늘려야 한다. → **범례를 요약 아래에 한 번만**
  둔다(회색 알약 견본 + "다른 일정"). 시안은 알약 바로 아래에 적어 두지만, 그 예시에서는
  알약이 달의 **마지막 주**에 있어 아래가 비어 있었다 — 가운데 주에 오면 그대로 못 옮긴다.

⚠️ **5/6 미선택 글자를 `#B3B3B3` 로 내렸다**(2026-09-07 요청: "색이 너무 짙어").
흰 배경에서 **2.1:1** 이라 본문 최소 4.5:1 에 못 미친다. 이 화면에서는 시안을 따르기로 한
결정이고, 고른 항목은 `textPrimary` + Bold + 라임 체크로 확실히 갈린다. 칩(1/6·2/6·4/6)의
미선택 글자는 `#F2F2F2` 배경 위라 그대로 `textSecondary` 를 유지한다.

⚠️ **⑤ 라임 테두리는 흰 배경에서 1.5:1 이라 WCAG 1.4.11(비텍스트 3:1)에 못 미친다.**
시안을 따르기로 한 결정이고, 버튼임을 알리는 것은 테두리만이 아니라 안의 문구다(글자는
