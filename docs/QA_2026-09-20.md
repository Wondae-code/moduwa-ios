## 1. ⭐ 2/6 "기타" 버튼 — ✅ 시안대로 14지역 + 기타 (`e74c8f5`)

한동안 "기타가 무엇이 되는가" 를 몰라 멈춰 있었다(자유 입력이냐, 목록에 없는 지역이냐).
**시안이 왔고 답이 거기 있었다** — 지역을 **12 → 14** 로 늘리고 맨 끝에 "기타" 칩 하나.
3열 5행, 포항·안동이 갈라지고 울산이 들어왔다.

⚠️ **옛 플랜이 지역을 잃지 않게** `TravelRegion.init?(storedValue:)` 를 뒀다. 서버 디코딩이
`flatMap(TravelRegion.init(rawValue:))` 라, 케이스 이름만 바꾸면 그 전에 만든 플랜이
**조용히 `nil` 이 되어** 회색 표지로 돌아간다. `pohangAndong` 은 `pohang` 으로 읽는다.

**"기타" 의 동작**: 고를 수는 있고(다음으로 활성) 추천 코스는 못 만든다. 지도는 담긴 장소로
맞추고 표지는 회색이다. 제목에도 안 들어간다 — "기타 여행" 은 제목이 아니라 오류로 읽힌다
(`titleLabel`). 자유 입력은 넣지 않았다: 슬러그가 없으면 추천도 지도도 표지도 전부 비는데,
입력만 받아 두면 **기능이 반쯤 죽은 채로** 들어간다.

## 2. "다음으로" 를 비활성/활성으로 — ✅ (`45399b6`)

값이 없으면 **버튼을 아예 안 그렸다**(`if hasValue`). 값을 고르는 순간 툭 나타나 화면이 흔들렸다.

⚠️ **그건 실수가 아니라 기록된 결정이었다** — 값이 없을 때 누르면 "나중에 할래요" 와 같은
동작이 되어 두 버튼이 같은 뜻을 두 번 말하기 때문이다. **비활성 버튼에는 그 걱정이 없다**
(눌리지 않으면 같은 동작이 아니다). 바꾸면서 **그 주석도 같이 고쳤다** — 안 고치면 다음
사람이 이유를 보고 되돌린다. 비활성 색은 `AuthPrimaryButton` 과 같은 규칙(`iconGray`)이다.

## 3. 플랜 카드 하단 블러 — ✅ (`9541d9d` · `5c2089c`)

**일정 탭 카드에는 이미 있었다.** 플랜 목록 카드에만 없어서, 두 곳이 같은 것을 나눠 쓰도록
`CardCoverBlur` / `CardCoverScrim` 으로 뺐다.

시안은 progressive blur(0→60)인데 **SwiftUI 에는 위치에 따라 반경이 변하는 흐림이 없다.**
반경을 실제로 올리려면 사본을 여러 장 겹쳐야 하고 표지가 `AsyncImage` 라 장수만큼 비용이
붙는다. 그래서 한 반경으로 흐린 사본 한 장을 만들고 **마스크로 농도를 아래로 갈수록 올린다** —
시안과 다른 점을 알고 택했다.

⚠️ 함정 둘을 컴포넌트 주석에 모았다:
- `blur(opaque: true)` — 기본값이면 흐린 사본의 가장자리가 투명해져 **테두리에 밝은 띠**가 생긴다.
- 표지 클로저가 **두 번 불린다** — `AsyncImage` 자체를 넘기면 **같은 사진을 두 번 받는다.**
  부르는 쪽에서 content 안에서 만들어 이미 받아 온 `Image` 를 넘긴다(그래서 `@escaping`).

**덤으로 드러난 것**: 일정 카드의 흐림 띠가 아래 204 만 덮어 **제목이 띠 바로 위에 걸려**
있었다. 밝은 사진(전주 경기전)에서는 흰 제목이 거의 안 보였다. 시안의 `Y 0% → 100%` 대로
카드 전체로 넓혔다 — 위쪽은 흐림 0·스크림 0 이라 사진이 그대로 보이므로 잃는 것이 없다.

## 4. ⭐ 일자 수정 — ✅ 줄면 그 날 일정이 지워진다 (`a282ae3` 외 5개)

⚠️ **2026-09-07 에 `#13` 으로 "패스" 처리됐던 것이다.** 그때는 고칠 수 있는 것이 제목·일정
순서·팀뿐이었고 **날짜·기간·지역이 없었다.** 이번에 ⭐ 중요 UX 로 다시 올라와 만들었다.

**기획 결정(2026-09-20 사용자)**: 기간을 줄이면 **잘려 나가는 날의 장소·메모를 지운다.**
마지막 날로 모으지도, 줄이는 것을 막지도 않는다 — 대신 **지우기 전에 말한다.**

- **줄이면** 사라질 것을 세어 바꾸기 버튼 위에 미리 적는다
  (`담아 둔 장소 9곳과 메모 2개가 사라져요`). 누르면 "되돌릴 수 없어요" 와 함께 한 번 더 묻는다.
- **늘리면** 새 날이 빈 채로 붙는다. 묻지 않는다.
- **시작일을 옮기면** Day 의 날짜만 바뀌고 장소는 Day 에 붙어 따라간다.
- 잘리는 날이 **비어 있으면 아무 말도 하지 않는다** — 잃는 것이 없는데 겁을 주면 다음 경고도 안 읽는다.

⚠️ **조사는 받침을 보고 고른다.** 처음엔 "가" 를 그냥 붙여 `17곳가 지워져요` 가 나왔다
(`33c7e7d`). `(스칼라 - 0xAC00) % 28 == 0` 이면 "가", 아니면 "이".

⚠️ **확인 창은 `alert` 다 — `confirmationDialog` 를 쓰면 안 된다.** iOS 26 에서 팝오버로
붙으면서 **취소 버튼이 사라진다**(2026-09-07 기록). 되돌릴 수 없는 삭제에는 예외가 없다.

⚠️ **목록·일정 카드가 들고 있는 플랜은 `days` 가 비어 있다**(`days: []`). 그대로 편집 화면에
넘기면 경고가 **한 줄도 안 뜨고**, 저장하는 순간 **모든 날이 지워진다.** 시트를 열기 전에
상세를 받아 온다(`openInfo`).

**함께 정리된 것** — 같은 값을 고치는 문이 네 곳에 흩어져 있었다:

| 상세의 날짜 줄 `›` | 제목까지 같이 | **날짜만** | `59a9b40` |

## 11. 지도 아이콘 굵기 — ✅ +0.4 (여행 상세 우상단)

⚠️ **이 아이콘은 선이 아니라 채워진 면으로 그려져 있다.** 바꿀 `stroke-width` 값이 없어서
같은 색 테두리를 둘러 면을 키웠다 — 결과는 같지만 **안쪽으로도 같이 두꺼워진다.**

**시안 값 "1" 은 쓰지 않았다.** 26pt 아이콘에서 1은 선폭의 절반이 넘는 값이라 **핀 속 흰 점이
거의 닫혔다.** 0.4 / 0.7 / 1 을 그려 비교하고 **0.4** 로 정했다(2026-09-20 사용자 결정) —
옆의 SF Symbol(연필·돋보기)과 무게가 맞는 자리다.

또 하나: 원본 그림이 이미 `x=0` 에 닿아 있어 테두리가 **왼쪽·위로 잘렸다.** `viewBox` 를
0.25 씩 넓혀 해결했다(그림 위치는 그대로).

💡 정석은 **디자이너가 원본을 굵게 다시 그려 주는 것**이다. 테두리 방식은 모서리가 약간
둥글어지고 안쪽으로도 두꺼워진다 — 지금 크기에서는 눈에 띄지 않는다.

## 13. 관광지·축제공연 → 이전 페이지 — ✅ 가설대로 고쳤다 (`45399b6`)

재현 경로 없이 코드만 보고 세운 가설이었고, 고친 뒤 시뮬레이터에서 관광지→축제·공연 연타에
**선택과 목록이 일치**하는 것을 확인했다. 원인은 `HomeViewModel.selectCategory` 였다:

```swift
func selectCategory(_ category: PlaceCategory, using service: any FeedService) async {
    selectedCategory = category
    setPlaces(firstPage: (try? await service.fetchRecommendedPlaces(...)) ?? [])
}
```

**먼저 보낸 요청을 취소하지 않고, 돌아온 응답이 지금 고른 카테고리의 것인지도 보지 않는다.**
관광지를 눌렀다가 곧바로 축제·공연을 누르면 두 요청이 경주하고, **늦게 도착한 쪽이 이긴다** —
축제·공연을 골랐는데 관광지 목록이 그려질 수 있다. 그 상태에서 카드를 누르면 "이전에 열었던
페이지" 로 간다.

덤으로 `try?` + `?? []` 라 **실패하면 조용히 빈 목록**이 된다 — 사용자는 "그 카테고리에
아무것도 없다" 로 읽는다.

**고친 방식**: 앞 요청을 `Task.cancel()` 로 끊고, 그래도 돌아온 응답은 **지금 고른 카테고리의
것일 때만** 쓴다. 취소만으로는 부족하다 — 이미 네트워크를 떠난 응답은 취소해도 도착한다.
실패는 빈 목록이 아니라 `placesError` 줄로 알린다(보던 목록은 그대로 둔다).

## 이동 수단 — ✅ 싣는다 (`be69a12`)

1/6 에서 **자차·뚜벅이·휠체어**를 묻고도 **추천 요청에는 빼고 있었다.** 플랜 저장(`PUT`)에는
실리는데 추천(`POST`)에만 없었다 — 자차와 뚜벅이에게 **같은 코스를 주고 있었다**는 뜻이다.

⚠️ 필드명은 **`mobilities`(복수)** 다. 내가 `mobility`(단수)를 제안했는데 서버팀이 바로잡았다 —
플랜의 `party` 안에 이미 `{"mobilities": ["walking"]}` 로 저장되고 있어서, 추천에만 새 이름을
만들면 **같은 것을 두 이름으로 부르게** 되고 한쪽을 고칠 때 다른 쪽이 조용히 어긋난다.

무엇이 달라지나(서버 측정):

| 고른 것 | 결과 |
|---|---|
| 자차 · 미전송 | 코스가 **바이트 단위로 같다** — 하위 호환 |
| 뚜벅이 · 휠체어 | 동선이 좁아진다 — 가평 39km → 14km, 통영 28km → 5km |
| 자차 + 휠체어 | 거리는 자차, **접근성은 휠체어** 기준. 차로 가도 도착해서는 휠체어로 다닌다 |
| 휠체어 | 미조사 장소를 더 세게 민다(가평 10/24 → 3/24). 거르지는 않는다 — 가평은 조사된 식당이 1곳뿐이라 걸러 내면 아홉 끼가 빈다 |

⚠️ **가평에서는 거리와 접근성을 동시에 만족할 수 없다.** 휠체어를 고르면 39km 다(뚜벅이 14km).
조사된 무장애 장소가 두 군에 흩어져 있어서다. 서버가 **접근성을 택했고 그대로 둔다** —
먼 것은 화면에 보이지만 못 들어가는 것은 가서야 안다. 무장애가 주제인 앱에서 둘 중
하나라면 접근성 쪽이다. 뒤집으려면 서버의 `foot_distance_mult` 한 줄이다.

이때 `notes` 에 `includes_unsurveyed` 가 실리고, 앱은 이미 그 문구를 갖고 있다(`CourseNote`).
